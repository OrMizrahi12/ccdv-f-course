# Module 4 on one page: Context Engineering & Agents

CCDV-F · two areas of the exam: Agents and Workflows (Domain 1, 14.7%) and Context Engineering (in Domain 6, 3.8%), about 10 of 53 items (hooks and the Agent SDK in depth come in Module 5) · checked against the Claude docs and Anthropic's engineering articles on 2026-10-09

| Lesson | Keep this |
|---|---|
| 4.1 Workflow or agent | A workflow runs model calls and tools through code paths you wrote; an agent directs its own process in a loop, choosing the tools and their order until it's done or hits a limit. Start with a single call and add steps only when they pay. Five workflow patterns: prompt chaining (with a gate in code), routing, parallelization (sectioning or voting), orchestrator-workers, evaluator-optimizer. Four checks before an agent: complexity, value, viability, cost of error. Then measure the same job both ways. |
| 4.2 Building the agent loop | Send with the tools; run every `tool_use`; send all the `tool_result` blocks back in one user message; repeat until `end_turn` or a stop you chose. Stops: a turn limit, a budget checked before each request (the next request's input plus `max_tokens`, priced as the worst case), a refusal or `max_tokens`, a tool that ends the task. Put a person right before the irreversible step, after your code's checks; a no ends the task in code. Task budgets (beta) are a soft hint, not a hard cap, and the countdown is visible only to the model: `max_tokens` and your own checks are the limits that hold. |
| 4.3 Context engineering | Every turn resends the whole conversation, and recall from the context drops as it grows (context rot): aim for the smallest set of high-signal tokens. Three levers: clear old tool results (context editing; by default it triggers at 100,000 input tokens and keeps the 3 most recent tool uses; each clear invalidates the cached prefix), compact older turns into a summary, or restart with a fresh context that carries only what the next part needs. Choose by the task, and measure. |
| 4.4 Getting knowledge into context | Under about 200,000 tokens (about 500 pages) you can include the whole knowledge base, and cache it. Past that, or when an answer must point at its source: chunk it, score the chunks (BM25 matches exact words; embeddings match meaning and need a provider; together they beat embeddings alone), and send the top few as `search_result` blocks with a source, a title and citations enabled, at the top level or from a tool. Let an agent search again, just in time. Test the retrieval. |
| 4.5 Subagents and supervisors | A supervisor plans, writes a self-contained brief for each part (objective, output format, tools and sources, task boundaries) and combines short reports; each subagent works in its own clean context. Agents use about 4× the tokens of chat, multi-agent systems about 15×: parallel subagents buy time and focus, not savings. They fit independent parts, not work where every agent needs the same context or the parts depend on each other. |
| 4.6 Agent memory | The memory tool (`memory_20250818`) is client-side: Claude asks for file operations under `/memories` and your code runs them. Resolve every path and refuse anything outside the folder (`../`, links, encoded tricks), and cap file sizes, because memory is read at the start of every task. Your own store keeps what a rule needs and enforces it in code. Choose the scope (session, user, project) on purpose. |
| 4.7 Four ways to build an agent | Every agent has a harness: the loop, the tools and the stops. Write it yourself; let the SDK's Tool Runner drive it (a manual loop where a person must approve); run Claude Code's loop and tools in your process with the Agent SDK; or have Anthropic host it with Managed Agents (agent, environment, session, events; long-running work in a sandbox; beta; not currently eligible for zero data retention or HIPAA; tokens plus running time; a session budget is a hard cap). Pick by who runs it, where, and what each gives up. |
| 4.8 Agent frameworks | Start with the API directly: many patterns are a few lines, and frameworks can obscure the prompts and responses underneath. Measure what a framework adds before you adopt it: packages and version changes (`pip install --dry-run`), and tokens per request. Spot the patterns in its spelling: a router is a classify step and a conditional edge; orchestrator-worker is a planner, workers and a synthesizer. Keep your own loop while it's small. |

## The four traps

| Trap | It sounds like | Why it's wrong |
|---|---|---|
| Make it an agent | "Rebuild it as an autonomous agent." "Put it in a framework to be production-grade." "Add more agents in parallel to save money." | When you can list the steps, a workflow does the job with fewer requests and is easier to test. A framework adds packages and a layer to debug. Parallel subagents buy time, not tokens. Start simple, measure, add complexity only when it pays. |
| Bigger context fixes drift | "Move to a larger context window." "Keep the whole history." "Paste the whole library into every request." | Recall drops as the context grows, and every turn pays for all of it. Fewer, fresher tokens fix drift: clear old tool results, compact, start a fresh context per part, retrieve only the passages that matter. |
| Ask it nicely | "Tell it in the system prompt to stop after a few tries." "Set a task budget so it stops in time." "Leave it a note: confirm before paying." | A prompt line is a request, a task budget is a soft hint, and a note is advice. Put a turn limit and a budget in your loop, a person's approval before the irreversible step (where a no ends the task), and the rule in a check your code enforces. |
| Share everything | "One conversation for every job." "Forward the supervisor's whole conversation as the brief." "One memory folder for all users." | The parts mix, every agent pays for all of it, and one user's data reaches another's. Give each part a clean context and a self-contained brief, bring back a short report, and scope memory to the user it belongs to. |
