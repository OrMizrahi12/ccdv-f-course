# Module 9 on one page: Shipping and reuse

| Lesson | Keep this |
|---|---|
| 9.1 From business need to requirements | Turn the customer's words into numbered requirements: functional ones with an acceptance test, infrastructure ones with a number (latency, volume, cost, residency, retention). Compute capacity and cost from your own logs, not from a guess. Check the deciding constraint before writing code: one of them can rule out a model. Map every requirement to the part of the architecture that meets it, and send the open questions back. |
| 9.2 The systems life cycle | Develop, implement, operate, maintain: waterfall, iterative and DevOps teams all move through those phases, at different speeds. Ship the way teams do: an issue with an acceptance test, a branch, a plan a person reviews, small commits with tests, a pull request with automated checks and a human review, a protected main branch, and a runbook entry for whoever operates it. Know what Claude did and what a person decided. |
| 9.3 Refactoring and modernization | Pin today's behavior with characterization tests, then refactor in small steps that each run them, and prove the tests would catch a break. Migrate in stages, never as one big change: a judge first, then the rules, a dependency map, a throwaway trial, implement-review-fix loops and a gate per stage. Scope the engagement on one page that the client, the team and security can sign. |
| 9.4 Where it runs | The Claude API, Claude Platform on AWS, Amazon Bedrock, Google Cloud and Microsoft Foundry differ in who operates the stack and processes the data, which features are available, how residency is set, how you're billed and what latency you see. Choose by the deciding requirement, not by brand or price. Make the platform one setting, let the app list the features each platform would break, and record the decision in an ADR. |
| 9.5 Versioning what ships | Know exactly what ships: the version, the commit, a config hash, each feature's model snapshot (in a lock with its status and earliest retirement date) and each prompt's locked version, checked before every release. Pin snapshots, never a moving alias. Use semantic versions and a changelog that names its evidence; a plugin's version must match its marketplace entry, and its dependencies get ranges (`~` patches only, `^` minor versions too). Watch deprecations: at least 60 days' notice. A model upgrade is a release: the migration checklist, the rule written first, evals against the baseline, every unfinished job read (the cause may be your own code), a canary where there's traffic, a pull request, and a rollback that is one revert. |
| 9.6 Accelerators and coordinated deployments | Split what stays (code, prompts, graders, tests) from what each deployment sets (content, audience, models, budget, key), and ship one package with an `init` that makes a deployment folder. Boundaries live in code, each with a test written first: the MCP server is told which deployment it serves and gets no key (a client's roots are only a hint), sensitive plugin values go to secure storage. One deployment per team or tenant, with its own workspace, credential, spend limit, data and logs; a coordinator reads status, never content. Prove it with a fresh clone that follows only the README. Give back through each project's documented channel: a minimal reproduction with versions, and security problems privately. |

## The four traps

| Trap | It sounds like | Why it's wrong |
|---|---|---|
| Newest is safest | "Point production at the newest alias." "Switch everyone to the new model on Friday." | An alias can move under you, and newer isn't proof of better for your task. Pin the snapshot, evaluate against the baseline, roll out to a share of traffic first, and keep a rollback one revert away. |
| Big bang | "Rewrite the service in one release." "Merge the whole migration as one PR." | Nothing shows what broke, and there's no step to return to. Tests first, then small stages, each through a review and a gate. |
| Pick by brand or price | "Use the platform everyone knows." "Take the lowest token price." | The requirement that decides (residency, a processor agreement, a feature, latency, volume) goes unchecked. Find it first and check it in the docs for that platform and model. |
| Copy-paste reuse | "Fork the repo for each client." "Put every client in one deployment and tell the prompt to keep them apart." | Forks drift, and a prompt isn't a data boundary. Ship one versioned, parameterized package and give each tenant its own bounded deployment. |
